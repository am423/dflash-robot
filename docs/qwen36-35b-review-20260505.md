# DFlash-Robot Review: Qwen3.6-35B-A3B

## Executive Summary

The dflash-robot project implements DFlash speculative decoding for GGUF models using llama.cpp. For Qwen3.6-35B-A3B (MoE, 3B active), we tested two verification modes across 10 HumanEval-style prompts on RTX 3090.

Key finding: DDTree mode (budget=8) is 17.5% faster on average but produces CORRUPTED OUTPUT on 1/10 prompts. The vLLM-compatible single-chain baseline is slower but 100% correct.

## Architecture

### How DFlash Works
DFlash is a parallel speculative decoding method:
1. Target model runs a forward pass and captures hidden states from selected layers
2. Draft model receives these hidden states + mask tokens as cross-attention input
3. Draft model produces logits for all block positions in parallel (non-causal attention)
4. Target model verifies the draft tokens in a single forward pass
5. Accepted tokens are committed; rejected tokens trigger rollback

### How DDTree Works (dflash-robot addition)
DDTree adds tree-structured verification on top of DFlash:
1. Instead of a single chain of draft tokens, explore a tree of alternatives
2. Use best-first search with a node budget to find high-probability paths
3. Verify the tree path with the target model
4. This can find better draft sequences but adds 2-5ms draft_logits overhead

### Qwen3.6-35B-A3B Specifics
- Architecture: MoE with 128 experts, top-8 routing + shared expert with sigmoid gate
- Active params: ~3B (vs 35B total)
- Model file: Qwen3.6-35B-A3B-UD-Q4_K_M.gguf (20.1 GiB on GPU)
- Draft model: z-lab/Qwen3.6-35B-A3B-DFlash (3.3 GiB safetensors, 91 tensors, hidden=2048)
- Tokenizer: Qwen/Qwen3.6-35B-A3B

## Performance Bottlenecks

### 1. Verify Compute Dominates (25-35ms vs 4-6ms draft)
The target model verify pass is 5-6x more expensive than the draft pass.
This is expected for a 35B (Q4_K_M) model on a single 3090.

### 2. MoE Routing Overhead
The target model runs full MoE routing for each verify pass:
- Router: gate_inp @ cur → softmax → top-8 selection
- 8 expert FFN paths (gate_proj, up_proj, down_proj × 8 experts)
- Shared expert FFN path
- Expert weight gathering and weighted sum

For batch_size=64 (typical verify window), this is ~24ms dominated by mul_mat_id ops.

### 3. DDTree adds 2-5ms draft_logits overhead
At budget=8, the tree search itself is cheap. At budget≥16, the
draft_logits cost (2.66ms) starts eating into the speedup.

### 4. Acceptance Rate is Lower than 27B
27B model: ~25% acceptance on HumanEval
35B-A3B model: ~16% acceptance on HumanEval
This is because the MoE model's hidden states are harder for the
draft model to predict, especially across expert routing changes.

## DDTree Correctness Issue (Detailed Analysis)

Prompt #5 (intersperse) produces corrupted output with DDTree:
```
Baseline: 466 198 2 318 266 678 2904 8 866 2843 2243 13 198 2 198 2 1061 1957 369 4098
DDTree:   220 115651 113282 97622 96326 2100 3709 96220 108838 96382 109599 95789 110191 220 95793 114584 96326 2100 220 98700
```

### Root Cause (Confirmed)

The corruption is NOT from DDTree's tree search taking sibling branches.
It's from the draft model being **confidently wrong** on this prompt.

Trace analysis shows:
- DDTree accepts ~3 tokens/step using the greedy chain (chain_seed=true)
- At step 59, the draft model predicts token 124620 with high confidence
- DDTree commits this token; the baseline would reject it (lower acceptance rate)
- Subsequent draft predictions cascade into garbage (115651, 113282, etc.)
- The baseline avoids this because it accepts fewer tokens per step, getting
  more frequent target model corrections

This is a **draft model calibration issue**, not a DDTree algorithm issue.
The draft model (z-lab/Qwen3.6-35B-A3B-DFlash) is confidently wrong on
certain input patterns, particularly after newline tokens in code.

### Guards Implemented

Two quality guards were added (both work correctly when triggered):

1. **Sibling walk guard**: If the tree walk takes a sibling branch (diverges
   from the greedy chain), truncate to the chain spine only.

2. **Per-token confidence guard**: If the draft model's top-1 log-prob at
   any depth is below -4.0 (~2% probability), truncate the accepted path.

Neither guard triggers on prompt #5 because the draft model's top-1
probabilities are above the threshold — the model is confidently wrong.

### Recommendation

- Use DDTree mode for throughput-critical applications where occasional
  corruption is acceptable (monitor for garbage token IDs)
- Use chain mode (--fast-rollback without --ddtree) for production where
  correctness is paramount
- Future: retrain the draft model with better calibration, or add a
  target-side sanity check that compares draft output against target
  distribution at each step
